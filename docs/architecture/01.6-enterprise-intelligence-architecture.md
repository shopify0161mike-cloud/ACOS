# 1.6 Enterprise Intelligence Architecture

## Purpose

This architecture defines how ACOS governs AI agents, models, prompts, memory, tools, knowledge sources, evaluations and safety controls as enterprise capabilities.

## Principles

1. AI decisions are governed, observable and attributable.
2. Agents operate with least privilege and explicit tool scopes.
3. Model selection is policy-driven and workload-aware.
4. Prompts and evaluations are versioned artifacts.
5. Memory is classified, bounded and retention-controlled.
6. Knowledge retrieval preserves source provenance.
7. High-impact actions require deterministic policy checks and, where required, human approval.
8. Model outputs are never treated as authoritative without validation appropriate to their risk class.

## Intelligence control plane

The intelligence control plane contains:

- agent registry and lifecycle management;
- model and provider catalog;
- prompt registry and release controls;
- tool authorization and orchestration policies;
- memory and context policies;
- knowledge-source governance;
- evaluation suites and quality gates;
- safety, risk and escalation controls;
- telemetry, cost and performance observability.

## Agent lifecycle

Agents progress through `draft`, `evaluation`, `approved`, `active`, `suspended` and `retired` states. Promotion requires named ownership, model policy, tool scope, knowledge scope, evaluation thresholds and rollback criteria.

## Model routing

Model routing considers task class, data classification, required modalities, latency target, quality target, cost ceiling, regional constraints, provider health and fallback eligibility. Fallbacks may not weaken security, residency or approval requirements.

## Prompt governance

Prompts are immutable by version. Every production execution records the prompt identifier, version, model policy, tool policy and evaluation baseline. Material prompt changes require re-evaluation.

## Tool orchestration

Tools are allow-listed per agent. Each invocation is subject to identity, scope, policy, budget, data classification and approval checks. Mutating tools require idempotency, audit and recovery controls.

## Memory architecture

Memory classes are session, working, episodic, semantic and profile memory. Each class defines permitted data, retention, encryption, access scope, deletion behavior and grounding rules. Sensitive information must not be persisted unless explicitly permitted.

## Knowledge architecture

Knowledge sources require ownership, classification, freshness expectations, ingestion policy, provenance and access controls. Retrieval results must preserve source references and confidence metadata.

## Evaluation architecture

Evaluation combines deterministic tests, model-graded tests, human review and production monitoring. Required dimensions include correctness, grounding, safety, policy compliance, tool-use accuracy, latency and cost.

## Safety and escalation

Unsafe, uncertain or policy-conflicting requests are blocked or escalated. High-impact decisions must expose evidence, confidence and approval state. Agents fail closed when required controls are unavailable.

## Observability

Every run emits correlation identifiers, agent and model versions, prompt version, tool calls, retrieved sources, token and cost usage, latency, policy decisions, evaluation signals and final disposition.

## Relationship to other architecture layers

- Capability architecture defines what intelligence capabilities exist.
- Domain architecture defines business ownership.
- Event architecture defines intelligence events.
- Execution architecture governs durable execution.
- Governance architecture supplies authority, risk and approval policy.
- Platform architecture supplies runtime, identity, secrets, messaging and observability.
