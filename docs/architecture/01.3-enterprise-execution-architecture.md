# 1.3 Enterprise Execution Architecture

Status: Canonical

## Purpose

The Enterprise Execution Architecture defines how ACOS turns governed plans and commands into durable, observable and reversible execution. It separates decision authority, workflow coordination, domain state mutation and provider side effects so that no execution path can bypass policy, budget, identity, approval or audit controls.

## Scope

This chapter governs:

- command intake and validation;
- policy and budget enforcement;
- authenticated human approvals;
- durable execution state;
- retries, timeouts and recovery;
- saga coordination and compensation;
- idempotency and replay protection;
- provider side effects;
- event publication;
- observability and audit evidence.

## Core Principles

1. Runtime coordinates work but does not own domain business state.
2. Domain services remain authoritative for their own state transitions.
3. Every material side effect is policy-authorized, budget-authorized, attributable and auditable.
4. Sensitive control failures fail closed.
5. Every command and side effect is idempotent or protected by an idempotency key.
6. Durable state is persisted before external effects are acknowledged as complete.
7. Compensation is explicit and never assumed to be a perfect rollback.
8. Human-exclusive decisions cannot be synthesized by autonomous workloads.
9. Events are emitted through a transactional outbox or equivalent durable publication mechanism.
10. Correlation, causation and execution identifiers propagate end-to-end.

## Execution Components

### Command Gateway

The Command Gateway accepts authenticated commands, validates contract version, resolves the target domain, assigns correlation metadata and rejects malformed or unauthorized requests before orchestration begins.

### Governance Pipeline

The Governance Pipeline evaluates identity, policy, risk, budget and approval requirements. It returns an immutable authorization decision bound to the command intent, resource scope, constraints, expiration and policy versions.

### Durable Runtime

The Durable Runtime persists execution instances, steps, attempts, leases, timers and compensation state. It is responsible for orchestration, recovery and coordination only.

### Domain Services

Domain services execute valid business state transitions. They enforce domain invariants, persist authoritative state and emit canonical domain events.

### Integration Boundary

The Integration Domain translates enterprise requests into provider-specific operations. Provider data and error models must not leak into domain contracts.

### Event and Audit Infrastructure

Enterprise Events publish versioned facts. Audit records retain decision evidence, actor identity, command intent, outcomes, errors and compensations.

## Canonical Execution Flow

1. Authenticate the caller or workload.
2. Validate the command envelope and contract version.
3. Resolve ownership and target domain.
4. Evaluate policy and risk.
5. Authorize budget or exposure where required.
6. Collect authenticated human approval where required.
7. Create a durable execution record.
8. Dispatch a domain command or integration operation.
9. Persist the resulting state transition.
10. Publish domain events through a durable outbox.
11. Record correlated audit evidence.
12. Complete, retry, compensate or escalate the execution.

## Execution State Model

Canonical states:

- `received`
- `validating`
- `governance_pending`
- `approval_pending`
- `scheduled`
- `running`
- `waiting`
- `retry_scheduled`
- `compensating`
- `succeeded`
- `failed`
- `compensated`
- `cancelled`
- `manual_intervention_required`

Terminal states are `succeeded`, `failed`, `compensated`, `cancelled` and `manual_intervention_required`.

## Command Envelope

Every executable command must include:

- command ID;
- command type and version;
- correlation ID;
- causation ID when applicable;
- idempotency key;
- actor or workload identity;
- target domain;
- requested intent;
- resource scope;
- issued timestamp;
- optional expiration;
- governance context reference;
- payload.

## Idempotency

The effective idempotency scope is the tuple of target domain, command type, resource scope and idempotency key. Repeated delivery must return the previously committed result or an equivalent deterministic response. A retry may not duplicate financial, fulfillment, publication or provider side effects.

## Retry Model

Retries are permitted only for failures classified as transient or explicitly retryable. Retry policy must define maximum attempts, exponential backoff, jitter, deadline and retryable error codes. Permanent, policy, validation and invariant failures are not retried automatically.

## Saga and Compensation Model

Cross-domain workflows use explicit sagas. Each forward action records its compensating action, preconditions and compensation limits. Compensation executes in reverse dependency order where possible. Irreversible actions require approval, containment and manual recovery procedures rather than fictional rollback.

## Approval Model

Approval requests must bind the approver to the exact intent, evidence, risk, budget, constraints and expiration. A changed command invalidates prior approval. Approval records are durable and replay-protected.

## Failure Handling

Failures are classified according to the canonical failure taxonomy. The runtime records the failure, evaluates retry eligibility, performs compensation where safe and escalates to manual intervention when automated recovery would violate an invariant or exceed delegated authority.

## Observability

Every execution emits structured telemetry containing execution ID, step ID, attempt, domain, command type, duration, outcome and error classification. Metrics, logs, traces and audit records must be correlated without embedding secrets or unnecessary personal data.

## Security Boundaries

- Execution workers use least-privilege workload identities.
- Provider credentials remain inside governed adapters.
- Runtime state cannot grant additional business authority.
- Governance decisions are immutable inputs to execution.
- Secrets are referenced, not stored in command or event payloads.

## Architectural Invariants

- No external side effect before required governance gates succeed.
- No direct cross-domain database writes.
- No unversioned executable command or event contract.
- No duplicate material side effect for a single idempotency scope.
- No silent loss of a committed domain event.
- No autonomous creation of human-exclusive approval.
- No retry after command expiration or authorization expiration.
- No compensation that violates a domain invariant.
