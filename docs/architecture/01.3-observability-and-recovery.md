# 1.3 Execution Observability and Recovery

Status: Canonical

## Purpose

This document defines the evidence, telemetry and operational controls required to understand, recover and prove every material ACOS execution.

## Correlation Model

The following identifiers must propagate across commands, workflows, domain events, provider operations, logs, traces and audit evidence:

- execution ID;
- correlation ID;
- causation ID;
- command ID;
- step ID;
- attempt number;
- actor or workload identity;
- target domain.

Provider request identifiers are retained as external references but never replace enterprise correlation identifiers.

## Telemetry Requirements

### Metrics

Required metrics include execution throughput, success rate, latency, queue age, retry rate, compensation rate, manual-intervention rate, dead-letter volume, governance denial rate and provider error rate.

### Logs

Logs are structured, timestamped and correlated. They record decisions and state transitions rather than secrets, raw credentials or unnecessary personal data.

### Traces

Distributed traces cover command intake, governance checks, orchestration, domain execution, persistence, event publication and provider operations. Sampling must preserve all failed, compensated, security-sensitive and high-value executions.

### Audit Evidence

Audit evidence is append-only and contains actor identity, intent, evaluated controls, policy versions, approval references, state transitions, outcomes and recovery actions.

## Health and SLO Signals

Execution health is evaluated using:

- availability of command acceptance;
- governance decision latency;
- workflow scheduling delay;
- step completion latency;
- event publication lag;
- provider adapter availability;
- reconciliation backlog;
- recovery time objective;
- unresolved partial-effect count.

## Recovery Model

### Worker Failure

Durable leases expire and another worker resumes from the last committed checkpoint. Work already acknowledged as complete is not repeated.

### Runtime Restart

The runtime reloads non-terminal executions, evaluates timers and continues from persisted state.

### Event Publication Failure

Committed domain events remain in the transactional outbox until publication succeeds. Duplicate delivery is tolerated through consumer idempotency.

### Provider Uncertainty

The Integration Domain reconciles provider state using enterprise and provider identifiers before retrying, compensating or escalating.

### Corrupt or Inconsistent State

The affected execution is quarantined. Automated mutation stops, evidence is preserved and recovery requires an approved repair procedure.

## Reconciliation

Periodic reconciliation compares runtime state, domain state, event delivery and provider state. Differences are classified as expected lag, recoverable drift, uncertain effect or integrity failure.

## Dead-Letter Handling

Dead-letter records retain the original envelope, failure classification, attempts, timestamps and evidence references. Replay requires authorization and must preserve the original identity and causation chain while assigning a new replay execution identifier.

## Operational Runbooks

Runbooks must exist for:

- stuck executions;
- repeated transient failures;
- uncertain provider effects;
- failed compensation;
- event backlog;
- governance infrastructure failure;
- expired approvals during execution;
- suspected duplicate effects;
- data integrity incidents.

## Invariants

- No material execution is uncorrelated.
- No committed event is silently discarded.
- No failed compensation is hidden as success.
- No recovery action bypasses governance.
- No replay changes the historical evidence of the original execution.
- No operational dashboard becomes the authoritative source of domain state.
