# 1.3 Canonical Execution Failure Taxonomy

Status: Canonical

## Purpose

This taxonomy gives every execution failure a stable class, retry policy and operational response. Error handling must be based on classification rather than free-form provider messages.

| Class | Meaning | Automatic retry | Compensation | Typical response |
|---|---|---:|---:|---|
| validation | Command or payload is structurally invalid | No | No | Reject and return contract errors |
| authentication | Caller identity cannot be established | No | No | Fail closed and record security evidence |
| authorization | Identity lacks delegated authority | No | No | Reject and audit |
| policy | Policy evaluation denied the intent | No | No | Reject with policy decision reference |
| approval | Required approval is absent, expired or invalid | No | No | Wait for new approval or cancel |
| budget | Budget or exposure authorization failed | No | No | Reject or wait for revised allocation |
| invariant | Domain invariant would be violated | No | Usually no | Fail and require command correction |
| conflict | Concurrent state changed or optimistic lock failed | Conditional | No | Reload state and retry within limit |
| transient_dependency | Temporary provider or infrastructure failure | Yes | Conditional | Backoff with jitter |
| rate_limit | Dependency rejected due to quota or throttling | Yes | No | Respect retry-after and deadline |
| timeout | Operation exceeded its bounded deadline | Conditional | Conditional | Reconcile outcome before retry |
| partial_effect | Side effect may have occurred but acknowledgement is uncertain | No blind retry | Yes or reconcile | Query authoritative provider state |
| permanent_dependency | Provider rejected a valid request permanently | No | Conditional | Fail, compensate and escalate |
| data_integrity | Corrupt, inconsistent or unverifiable state detected | No | No | Quarantine and manual intervention |
| security | Suspected credential, identity or tampering incident | No | Containment only | Stop execution and alert security |
| capacity | Internal resources unavailable or saturated | Yes | No | Queue, shed load or retry |
| cancellation | Execution was cancelled by authorized intent | No | Conditional | Stop safely and compensate where defined |
| compensation | A compensating action failed | Conditional | Further compensation only if defined | Manual intervention required |
| unknown | Failure cannot yet be safely classified | No | No | Fail closed and escalate |

## Required Error Envelope

Every execution error must include:

- stable error code;
- failure class;
- human-readable summary;
- retryable boolean;
- execution ID;
- step ID and attempt;
- correlation ID;
- source domain or adapter;
- timestamp;
- optional retry-after;
- optional provider error reference;
- redacted diagnostic details.

## Retry Rules

1. A retryable flag may only be true for approved classes.
2. Timeouts and partial effects require reconciliation before another side effect is attempted.
3. Unknown failures are never retried blindly.
4. Retry deadlines may not exceed command, approval or authorization expiration.
5. Repeated failures beyond the configured threshold move the execution to manual intervention or a dead-letter process.

## Escalation Rules

Immediate escalation is required for security, data integrity, unknown partial effects, failed compensation and repeated policy infrastructure failures. Escalation evidence must contain the current state, completed effects, unresolved effects, attempted recovery and safe next actions.
