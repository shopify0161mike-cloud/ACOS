# 1.1 Capability Traceability Model

## Purpose

This document defines how ACOS traces enterprise capabilities from constitutional authority through policy, architecture, implementation, runtime evidence and business outcomes.

Traceability exists to prove that each material capability is authorized, correctly implemented, safely operated and continuously accountable.

## Traceability chain

The required chain is:

```text
Constitutional rule
  -> Enterprise capability
  -> Governing policy
  -> Architecture decision
  -> Domain ownership and contract
  -> Implementation reference
  -> Validation evidence
  -> Runtime execution evidence
  -> Operational telemetry
  -> Business outcome
```

A broken link is an architecture control failure. For enterprise-critical capabilities, missing traceability must fail closed.

## Sources of truth

| Concern | Canonical source |
|---|---|
| Constitutional authority | `docs/constitution/ACOS-CONSTITUTION.md` and constitutional registry |
| Capability identity and ownership | `config/capabilities/registry.yaml` |
| Capability structure | `schemas/capability-registry.schema.json` |
| Architecture decisions | `docs/adr/` |
| Domain ownership and contracts | Domain architecture and contract registries |
| Implementation | Versioned implementation references in the capability registry |
| Validation | CI results, tests, schema checks and release evidence |
| Runtime execution | Durable execution records and correlated events |
| Audit | Append-only audit evidence managed by `CAP-GOV-AUD-001` |
| Outcomes | Governed analytics and outcome records |

## Capability-to-policy traceability

Every capability must declare the policies that govern its material decisions and side effects through the `policies` field.

Policy links must be:

- resolvable to a canonical policy identifier;
- appropriate to the capability authority and risk;
- evaluated before material side effects;
- included in audit evidence;
- updated when policy scope or capability meaning changes.

A capability with execution authority but no applicable policy linkage is incomplete.

## Capability-to-ADR traceability

An ADR is required when a capability change introduces a material, cross-domain, difficult-to-reverse or constitutionally sensitive architecture decision.

Typical triggers include:

- new or changed authority levels;
- new bounded-domain ownership;
- a cross-domain dependency;
- a material event or data contract;
- a new external provider class;
- a change to criticality or recovery objectives;
- a human-exclusive decision boundary;
- a new autonomy or orchestration model;
- a migration that changes the source of truth.

ADR references may be added to implementation or architecture documentation until the registry schema includes a dedicated ADR field.

## Capability-to-implementation traceability

The `implementation_refs` field identifies the concrete artifacts that realize the capability.

A valid implementation reference should identify one or more of:

- service or module;
- database migration;
- API or event contract;
- workflow definition;
- infrastructure component;
- test suite;
- release specification;
- operational runbook.

Implementation references must not point only to a vendor product or UI screen. They must identify the controlled ACOS artifact that owns the integration or behavior.

## Capability-to-runtime traceability

Every material execution must carry a correlation context containing, where applicable:

- capability ID;
- execution and step ID;
- actor or workload identity;
- authority level;
- policy decision references;
- approval reference;
- risk and budget decision references;
- idempotency key;
- input and output contract versions;
- emitted event identifiers;
- rollback or compensation evidence;
- audit evidence reference.

This context must remain intact across domain and provider boundaries.

## Capability-to-outcome traceability

Every operational capability must define metrics in the registry. Metrics must demonstrate at least one of:

- business value;
- reliability;
- policy compliance;
- risk containment;
- operational efficiency;
- human intervention;
- cost or exposure;
- data quality;
- customer outcome.

Metrics without an accountable owner or decision use are telemetry, not governance.

## Minimum traceability controls

For every capability, automated or governed review must be able to establish:

1. the capability exists in the canonical registry;
2. its identifier is unique and structurally valid;
3. its owner and authority are explicit;
4. its dependencies resolve and are acyclic;
5. its policies are declared;
6. its events and data ownership are explicit;
7. its acceptance criteria are testable;
8. its implementation references are attributable when implemented;
9. its criticality is consistent with recovery objectives;
10. runtime evidence can be correlated to the capability;
11. material changes retain review and decision evidence;
12. deprecated capabilities have migration and retirement evidence.

## Traceability states

| State | Meaning |
|---|---|
| Complete | All required links exist and are validated |
| Partial | Capability is approved or planned, but implementation or runtime evidence is not yet expected |
| Degraded | A previously valid link is stale, unresolved or inconsistent |
| Non-compliant | A required governance, authority or evidence link is absent |
| Retired | Operational links are closed and historical evidence is retained |

A `C4` capability may not enter or remain operational in a degraded or non-compliant traceability state.

## Change impact analysis

Before approving a material capability change, the reviewer must evaluate impact on:

- constitutional rules;
- policies and approvals;
- upstream and downstream capabilities;
- bounded domains;
- events and contracts;
- data ownership and retention;
- security classification;
- criticality and recovery objectives;
- implementation references;
- tests and CI controls;
- observability and audit evidence;
- deprecation or migration plans.

## Validation roadmap

Current automated controls validate registry structure, identifiers, dependencies, cycles and canonical diagrams.

The next traceability controls should validate:

1. policy references against the canonical policy registry;
2. implementation references against repository artifacts or approved external identifiers;
3. event naming and version conventions;
4. criticality-to-recovery-objective rules;
5. required audit and identity dependencies for sensitive authority levels;
6. documentation links and architecture index integrity;
7. ADR requirements for material registry changes.

These controls should be implemented as reusable scripts and executed locally and in GitHub Actions.
