# 1.2 Context Mapping Catalog

Status: Canonical

This catalog defines the approved Domain-Driven Design relationship patterns between ACOS bounded contexts.

## Approved patterns

### Customer–Supplier

The upstream domain publishes a stable contract and accepts prioritized needs from downstream consumers without transferring ownership.

Used for Product to Brand, Brand to Marketing, Orders to Fulfillment, Policy to Risk and Runtime to Provider Integration.

### Published Language

A versioned event or service schema is the shared language. Implementations remain private to each context.

Used for enterprise events, policy decisions, budget decisions, approval outcomes and integration-operation results.

### Open Host Service

A domain exposes a governed service for multiple consumers. Access is authenticated, versioned, observable and policy-controlled.

Used for Policy Evaluation, Budget Authorization, Identity Verification, Audit Append, Knowledge Retrieval and Event Publication.

### Anti-Corruption Layer

A translating boundary prevents external or legacy models from entering the domain language.

Mandatory for commerce, payment, supplier, logistics, advertising, identity and knowledge providers.

### Partnership

Two contexts coordinate roadmaps and compatibility because neither can evolve independently without material operational risk.

Limited to Executive Coordination with Runtime and Runtime with Enterprise Events. Partnerships do not create shared data ownership.

### Separate Ways

Contexts intentionally remain independent where integration cost exceeds enterprise value. Data exchange, when necessary, uses manually governed exports or analytical projections.

### Conformist

Prohibited for core and governance domains. It may be approved for low-risk generic infrastructure only when the external model is already an accepted standard and an ADR records the decision.

### Shared Kernel

Disallowed by default. A minimal shared kernel requires named owners, semantic versioning, compatibility tests and an ADR. Shared database schemas are never considered a shared kernel.

## Canonical relationships

| Upstream | Downstream | Pattern | Contract |
|---|---|---|---|
| Market Intelligence | Product | Published Language | Market opportunity events |
| Supplier | Product | Customer–Supplier | Supplier qualification events |
| Product | Approval | Published Language | Acceptance request event |
| Approval | Product and Brand | Published Language | Human decision events |
| Product | Brand | Customer–Supplier | Accepted product projection |
| Brand | Marketing | Customer–Supplier | Brand identity and claim constraints |
| Commerce Finance | Budget Governance | Published Language | Unit economics event |
| Budget Governance | Marketing and Runtime | Open Host Service + Published Language | Authorization service and decision events |
| Orders | Fulfillment | Published Language | Order lifecycle events |
| Policy | governed domains | Open Host Service + Published Language | Policy evaluation and decision events |
| Identity | Approval and Runtime | Open Host Service | Identity verification |
| Executive Coordination | Runtime | Partnership | Governed plan contracts |
| Runtime | Enterprise Events | Partnership | Publication and replay contracts |
| Runtime | Provider Integration | Customer–Supplier | Canonical provider-operation commands |
| Provider Integration | external providers | Anti-Corruption Layer | Provider adapters |
| Knowledge | Market Intelligence | Open Host Service | Governed evidence retrieval |
| Audit | all domains | Open Host Service | Append-only evidence service |

## Governance

Each relationship must identify upstream and downstream ownership, contract owner, compatibility policy, security classification, failure semantics and retirement process. Changes to a core-domain or governance relationship require architecture review and CI validation.
